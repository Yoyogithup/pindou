# Codex、Qoder 与用户协作协议

最后更新：2026-07-03

## 共同事实来源

任何 Agent 开始工作时，按需读取：

1. `docs/development_status.md`
2. `docs/development_schedule.md`
3. 与任务有关的 `docs/decisions/`
4. 产品、技术或测试专项基线
5. `apps/consumer/AGENTS.md`（修改消费者端代码时）

聊天记录和阶段 handoff 不是当前状态的权威来源。

## 角色规则

- 用户：确定产品意图、授权外部发布、执行真机验证、确认最终体验。
- 实现者：修改代码、补测试、运行验证、更新任务记录。
- 审查者：独立读取需求和差异，检查正确性、回归、边界与测试证据。
- 默认由 Qoder 实现、Codex 审查；也可以反向，但同一轮不得既实现又把自己当作独立审查者。

## 标准开发交接包

实现者交给审查者时必须提供：

- 任务 ID、目标和明确不做的范围。
- 基线分支、commit 和工作树状态。
- 修改文件与关键设计。
- 执行过的测试命令和真实结果。
- 未完成项、风险和需要重点审查的位置。
- 是否更新 `development_status.md` 与 `development_schedule.md`。

审查者输出：

- 按 P0/P1/P2 排序的可操作问题。
- 独立验证命令与结果。
- `通过`、`修复后复审` 或 `阻断` 的明确结论。

## 避免冲突

1. `development_schedule.md` 中同一任务只允许一个“当前负责人”。
2. Agent 接手前先检查分支、`git status` 和任务状态。
3. 不覆盖其他 Agent 的未提交修改；发现重叠时停止并说明。
4. 交接结论写入仓库，不依赖聊天上下文。
5. review handoff 可以保留历史细节，但不得继续充当当前任务账本。

## 真机 Bug 交接

真机问题使用 `pindou-device-debug`。修复者完成代码后只能标记“待真机复测”；用户确认通过后，协调者才更新为“已完成”。复测失败时保留原编号并追加新的尝试、commit 和部署 URL。

## GitHub 协作

- 一项任务一个分支和 PR。
- PR 描述写明目标、影响、验证和风险。
- 自动化检查通过不等于真机通过。
- 稳定 tag 只能指向通过对应验收门槛的 commit。
- 不上传用户图片、生成输出、密钥和第三方参考源码。
