# 0003：采用四层版本与恢复体系

- 状态：已接受
- 日期：2026-07-03
- 参与者：用户、Codex
- 影响范围：Git、GitHub、CI、部署、真机测试和恢复

## 背景

阶段 E 的消费者代码、测试和文档长期只存在于本地未提交工作树中。现有 `v2.0` 标签只能恢复到 FastAPI 阶段，无法恢复消费者 H5。继续开发会增加误改后无法回归以及本地数据丢失的风险。

## 决定

采用四层版本体系：

1. Commit：一个可理解、可验证的小改动。
2. Branch + Pull Request：隔离一项功能或 Bug，并承载审查。
3. Tag + GitHub Release：标记经过验证的稳定节点。
4. Deployment：将真机可访问版本绑定到明确 commit 和候选版本。

`main` 只代表已验证主线。分支命名：

```text
feature/DEV-###-description
fix/BUG-F-###-description
docs/DEV-###-description
codex/description
qoder/description
```

## 合并与发布规则

1. 默认不直接在 `main` 开发。
2. 合并前必须通过相关自动化测试、build 和 lint。
3. 通过 PR 记录改动、验证结果、风险和审查结论。
4. 阶段或发布候选使用标签；现有 `v2.0` 保留为历史节点。
5. 阶段 F 建议使用 `v2.1.0-device-rc.N`，四类真机通过后发布 `v2.1.0`。
6. 已合并错误优先使用 `git revert` 生成可审计的撤销提交，不重写共享历史。
7. 禁止未经明确授权使用 `git reset --hard`、强制推送或删除用户本地资产。

## 数据边界

GitHub 可以保存自研代码、测试、文档、脱敏且有授权的 fixture、技能和配置示例。不得上传用户原图、密钥、未脱敏测试材料、生成输出、依赖缓存或第三方嵌套仓库源码。

## 恢复策略

- 未合并错误：放弃或修正任务分支，稳定 `main` 不受影响。
- 已合并错误：revert 对应 commit 或 PR。
- 部署错误：重新部署上一稳定 tag。
- 单文件错误：从已知稳定 commit 恢复指定文件。
- 用户数据：使用独立受控备份，不进入 GitHub。

## 重新讨论条件

- 建立多人团队并需要更严格的审批或发布职责。
- 引入数据库迁移、后端状态或不可逆数据变更。
- 项目拆分成独立发布的多个仓库。
