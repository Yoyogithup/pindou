# 0001：采用统一的 pindou 开发工作法

- 状态：已接受
- 日期：2026-07-03
- 参与者：用户、Codex
- 影响范围：开发、测试、审查、文档、Codex/Qoder 协作

## 背景

项目已经拥有产品、技术、测试和多个阶段交接文档，但“当前事实”散落在不同文件中。`development_status.md` 一度仍写着消费者 H5 未开发，而实际阶段 E 已完成并通过五轮审查。项目需要一个开发闭环，避免代码进度与文档记忆分离。

## 决定

建立 `pindou-develop` 技能，提供六种工作意图：

- `dev`：开发、完整验证、同步状态与计划。
- `plan`：拆解和调整任务。
- `test`：按风险选择单测、构建、lint、浏览器或真机验证。
- `review`：独立审查并登记阻断项。
- `quest`：结合权威文档和代码回答问题。
- `status`：汇总当前事实、阻断项和下一步。

项目只保留两份动态权威文档：

- `docs/development_status.md`：唯一“当前事实”。
- `docs/development_schedule.md`：唯一任务账本。

产品、技术和测试方案继续作为专项基线；阶段 review handoff 只作为历史证据。

## 执行规则

1. 开始工作前检查 Git 状态、当前分支和相关权威文档。
2. 一项开发任务使用稳定任务 ID 和独立分支。
3. 修改只扩展到用户授权的范围，保护本地数据和第三方参考仓库。
4. 按风险完成验证；不能用“语法无误”替代业务验证。
5. 完成后更新状态与任务账本；架构、产品或测试基线改变时再更新专项文档。
6. 实现者与审查者尽量分离；默认 Qoder 实现、Codex 审查，反向亦可。

## 后果

- 项目状态更容易被新 Agent 恢复。
- 每次任务多一道文档同步成本，但减少重复调研和错误交接。
- `development_status.md` 必须保持短而准确，不能重新膨胀为历史日志。

## 重新讨论条件

- 项目拆分成多个独立仓库或拥有多个并行发布产品。
- 动态文档维护成本明显大于收益。
- Codex 或 Qoder 的技能发现机制发生重大变化。
