## 3. 已确认的产品决定

以下不是待讨论项，开发时直接执行：

1. 新增独立消费者 H5，不把现有 FastAPI 页面硬改成用户端；
2. 页面以手机 390×844 为首要视口；
3. 用户上传图片后，选择用途和模式，再主动点击生成；
4. 用途保留原图比例，最长边分别为：挂件 29、冰箱贴 58、摆件 72；
5. 模式为：新手、标准、细节；具体参数见技术方案；
6. 默认选择：冰箱贴 + 标准；
7. V0 默认不保留背景；
8. 必须独立生成图纸 PNG 和豆子用量 PNG；
9. 用量图只显示色块、MARD 色号和数量，不显示不存在或未经核验的颜色名；
10. 微信内置浏览器属于硬性验收范围；
11. 核心算法采用洁净重写；
12. 一期不公开推广，页脚开源/第三方入口可保持低视觉权重；
13. 不做登录、支付、社区、PWA、云端历史、AI 精细抠图、复杂编辑器和默认 CSV 入口。

## 4. 代码与版权边界

### 可以做

- 阅读参考项目，理解用户可见行为和问题；
- 根据产品需求重新设计接口、数据模型、算法和测试；
- 使用公开数学知识，如颜色空间、距离计算、图像采样、连通区域和 flood fill；
- 选择许可证兼容的通用第三方依赖，并记录到 `THIRD_PARTY_NOTICES.md`。

### 禁止做

- 从 Zippland 复制或改写源码、注释、测试、文件结构或大段实现；
- 复制它的 `colorSystemMapping.json`；
- 复制上游图片、品牌、水印、二维码或页面文案；
- 从 `reference-projects/` 运行时 import；
- 直接修改参考仓库作为产品实现；
- 在未确认来源时，把现有占位色库称为完整 MARD 生产色板。

参考项目只作为只读研究材料。若不确定某段实现是否属于洁净重写，请停止复制，基于需求重新写接口和测试。

## 5. 仍缺少的关键输入

目前没有可直接用于生产的、来源可追溯的完整 MARD 色号—HEX 数据。

允许的开发策略：

- 先使用专门的测试 fixture 小色板开发接口和自动化测试；
- 将生产色板加载层独立出来；
- 在 UI 明确标记开发数据，不能以占位数据发布。

发布前必须补齐：

- 完整 MARD 色号；
- 对应 HEX；
- 数据来源、取得日期、版本和使用边界；
- 唯一性和合法性校验。

这个缺口不会阻止工程骨架和算法测试，但会阻止真实色号版本发布。

## 6. 推荐架构

```text
apps/consumer/                 新增 Next.js 消费者 H5
├─ src/app/generate/           单页生成流程
├─ src/features/generator/
│  ├─ model/                   类型和 preset
│  ├─ core/                    洁净重写算法
│  ├─ export/                  两种 PNG 和保存
│  ├─ components/              mobile-first UI
│  └─ hooks/                   页面状态与资源释放
└─ tests/                      单元、集成和 E2E

web/                           保留现有 FastAPI 内部工作台
reference-projects/            只读第三方参考，不属于产品代码
```

详细文件树见 `docs/technical_plan_v0.md`。

核心数据流：

```text
File
→ 本地解码和方向修正
→ 按最长边生成网格
→ MARD 映射
→ 相似色合并 / 小区域清理 / 颜色硬上限
→ 去背景
→ 唯一一次用量统计
→ PatternDocument
→ 图纸 PNG + 豆子用量 PNG
```

两种导出必须消费同一个 `PatternDocument`。禁止在两个渲染器里分别重新统计豆数。

## 7. 数据与部署

V0 不需要数据库、图片处理 API 或业务服务器。

- 消费端部署为 HTTPS 静态网页；
- 用户原图、像素、网格和生成结果仅存在用户浏览器内存；
- 用户主动保存后，PNG 进入其手机相册或下载目录；
- 刷新或关闭页面后，未保存结果消失；
- 页面 JS、CSS、字体和色板由静态托管/CDN 提供；
- 现有 FastAPI 工作台与消费者端分开，不进入朋友使用的主链路；
- 一期若限制朋友访问，可使用静态站点入口访问码，不需要用户数据库。

不得把图片、Blob、base64 或网格上传到分析服务。发布前用 Network 面板验证。

## 8. 第一轮开发顺序

不要一上来做完整页面。建议按以下顺序提交小而可审查的变更。

### 阶段 A：工程骨架

1. 建立 `apps/consumer/`；
2. 配置 TypeScript、测试和静态构建；
3. 建立 `/generate` 空页面和基础移动布局；
4. 建立 `PatternDocument`、`EffectivePreset`、`ExportAsset` 类型；
5. 不接数据库，不修改 FastAPI 主流程。

验收：应用能构建、测试能运行、390 px 无横向溢出。

### 阶段 B：Preset 和纯算法

1. 实现九组 `resolvePreset`；
2. 实现网格尺寸计算；
3. 用小 fixture 色板实现颜色距离与稳定映射；
4. 实现相似色合并、小区域清理和颜色硬上限；
5. 实现 `calculateUsage`；
6. 优先完成对应单元测试。

验收：测试方案第 4–8 节通过；`totalBeads === sum(usage.count)`。

### 阶段 C：V0 去背景

1. 优先尊重 PNG 透明通道；
2. 实现边缘颜色聚类与置信度；
3. 仅删除与边界连通的背景；
4. 低置信度时进入“点选背景重试”；
5. 支持撤销和重选，不扩展为逐格编辑器。

验收：不会无提示大面积删除主体；背景格成为 `null` 且不计豆数。

### 阶段 D：两个独立 PNG

1. 实现 `renderPatternPng`；
2. 实现完全独立的 `renderUsagePng`；
3. 使用 `canvas.toBlob`；
4. 用量图 1080×1350，支持最多 28 色；
5. 清除所有上游品牌、水印、二维码和旧域名。

验收：只调用 `renderUsagePng` 也能得到合法图片；两张图数字一致。

### 阶段 E：用户页面

1. 上传和本地预览；
2. 用途、模式选择；
3. 明确的生成按钮和状态机；
4. 两张结果卡；
5. 大图全屏、双指缩放、双击、平移、加减和复位；
6. 真实 `<img>` 长按；
7. 保存按钮、打开原图和能力检测后的系统分享；
8. Object URL 生命周期管理。

验收：完整主流程和大图测试通过。

### 阶段 F：真机和部署

1. 静态构建并部署到 HTTPS 测试地址；
2. iPhone Safari；
3. iPhone 微信内置浏览器；
4. Android Chrome；
5. Android 微信内置浏览器；
6. 验证图片数据无网络外发；
7. 记录机型、系统、版本和真实保存结果。

没有真机记录，不能宣称“手机保存已完成”。

## 9. 关键参数

用途：

| 用途 | 最长边 | 坐标间隔 |
|---|---:|---:|
| 挂件 | 29 | 5 |
| 冰箱贴 | 58 | 10 |
| 摆件 | 72 | 10 |

模式：

| 模式 | 采样 | 相似阈值 | 最小色块 |
|---|---|---:|---:|
| 新手 | dominant | 32 | 3 |
| 标准 | dominant | 24 | 2 |
| 细节 | average | 14 | 1 |

颜色硬上限：

| 用途 \ 模式 | 新手 | 标准 | 细节 |
|---|---:|---:|---:|
| 挂件 | 8 | 12 | 16 |
| 冰箱贴 | 10 | 16 | 24 |
| 摆件 | 12 | 20 | 28 |

这些是首轮校准基线，不是未经验证的最终效果参数。调整必须附样图对比和测试变化，不能凭感觉悄悄改常量。

## 10. 发布硬门槛

以下任一项未满足，不得把任务标记完成：

- 图纸 PNG 和豆子用量 PNG 不是两个独立文件；
- 用量图只能通过 CSV 获得；
- 图纸、用量图和内存统计不一致；
- 背景格被计算为豆子；
- 最终颜色超过 preset 上限；
- 72 格图无法放大读取色号；
- 保存只实现了一个未经真机验证的 `download` 按钮；
- 微信内置浏览器没有验证记录或有效兜底；
- 用户图片被上传；
- 使用了未记录来源的生产色板；
- 复制了参考仓库代码或数据；
- 自动化测试、构建或关键 E2E 失败。

完整用例见 `docs/test_plan_v0.md`。

## 11. 每次提交要求

开发者应在交付 CR 前提供：

1. 改动目标和明确范围；
2. 主要文件列表；
3. 实际运行的测试命令及结果；
4. 未运行的测试及原因；
5. 390×844 页面截图；
6. 两张示例导出图；
7. 若涉及手机保存，提供真机矩阵；
8. 若涉及算法参数，提供前后样图和统计差异；
9. 已知问题和下一步；
10. 确认未复制参考仓库代码或色板 JSON。

建议按阶段拆分提交，不要把工程骨架、算法、全部 UI、依赖升级和 FastAPI 修改揉成一个巨大提交。

## 12. CR 重点

后续 Code Review 将重点检查：

- 是否符合产品范围，而不是复刻专业工作台；
- 洁净重写边界是否清楚；
- 数据模型是否只有一个统计来源；
- null 背景、颜色硬上限和总豆数不变量；
- 用量 PNG 是否真正独立；
- Canvas、Blob、Object URL 是否正确释放；
- 手机保存是否有多层兜底及真机证据；
- 大图是否真的可读，而非只做 CSS 缩略；
- 图片是否发生任何网络外传；
- 无障碍缩放是否被禁用；
- 静态部署是否真的不依赖数据库或 FastAPI；
- 测试是否覆盖失败路径和边界值。
